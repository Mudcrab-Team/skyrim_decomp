# Form-factory deleting destructors

Two Bethesda factory templates account for **199 local comparator passes and 17,114 bytes** on `sse-steam-1-7-104`. MSVC emits the deleting destructor from a virtual destructor that unregisters the form type. The derived factory inherits that cleanup. Its own primary vtable identifies the derived entry even when its body writes the base factory's vtable.

| Opportunity | Functions | Code bytes | Evidence and cost |
| --- | ---: | ---: | --- |
| Slot-zero deleting destructors of the two factory templates | 199 | 17,114 | One destructor body and two kinds of explicit instantiation. Primary RTTI supplies the owner, form type and object category parameters. All passed locally. |
| Ordinary factory teardown entry points | 118 | 6,136 | Indexed 52-byte callers of the same unregister helper, outside marked, matched and live-claimed work at survey time. No slot-zero owner. Base and derived ordinary destructors can compile identically. Attribution and boundary checks remain. |
| Other factory subclasses | 3 | 258 | Indexed 86-byte callers of the same helper in other slot-zero owners. Each needs its own inheritance and declaration evidence. |

The last two rows are survey upper bounds. The survey used call relationships, RTTI and extent sizes for ranking. The production generator starts from primary vtables, independently of function size. On the initial scan, 216 template entries passed the ownership and call checks. The final extent sweep rejected 17 whose entries lay inside a longer indexed range. No accepted RVA overlapped any of the 13 sibling batch classifiers from static-data through memory-factory generation, a tracked reconstruction marker, or an active contributor claim in the checked snapshot.

## Verification

- The split uses the low bit of the first SHA-256 byte of the ASCII form-class name. Even goes to development, including the earlier AlchemyItem prototype. Both factory kinds for a form stay together. The earlier survey inspected RTTI across the population. The holdout tests the C++ template on previously uncompiled form types.
- The first development build with a defaulted interface destructor missed all 126 initial development extents, emitting 76 bytes instead of 86. An explicit empty interface destructor restored the vptr transition and all 126 passed. The overlap check subsequently excluded ten development and seven held-out entries before the final comparison.
- The frozen template passed **116/116 development** (9,976 bytes) and **83/83 held-out** (7,138 bytes) on the first held-out evaluation. Every report covered the complete primary extent, both direct calls, vtable references, unwind information and the runtime termination import. Each object function also passed the published normalized target hash locally. A repeat generated byte-identical source, tasks, bindings and recipe.
- The earlier prototype omitted the full termination-thunk binding. Supplying the six-byte `__std_terminate` thunk found by `compare_runtime.termination_thunk` lets the ordinary comparator check its import identity and EH action. The comparator and recipe are unchanged.
- These are one-host results from pinned MSVC 19.16.27054 under Wine, comparator `0.6.1-runtime`. No second-host comparison or admitted review of the generated functions was performed for this contribution.

## Reproduce

Use Python with `iced-x86==1.21.0`, a configured contributor compiler and access to the contributor claim index. The executable must match the hash in `builds/target.json`. Use a fresh output directory for each run.

```sh
python3 tools/form_factory_generate.py --exe "$SKYRIM_EXE" --out .local/form-factories --compare
python3 -m unittest discover -s tests -p test_form_factory_generate.py
```

Add `--split development` or `--split held-out` to reproduce a partition. The snapshot contains three headers, two C++ units, the recipe, per-unit task and symbol maps, and per-function comparator reports. Changing the inventory or live claims can change the eligible population.

## Sources and limits

Repository revision `d1be313881`, pinned Steam image, public target hashes, community extents `CRASHLOGGER_PDB(59818@2026.10.24)`, and virtual declarations from `COMMUNITY(CharmedBaryon/CommonLibSSE-NG@b93280e, MIT)`. Exposure is mixed. Primary vtables, complete object locators, base descriptors and the immediate form ID establish the template identities. The interface's virtual declarations use the community header. The unregister helper's spelling and exact integral typedefs are stand-ins. Only the deleting destructors were compared. In particular, the constructor used to instantiate the derived vtable carries no constructor match claim.

All five generated source files passed compact source lint and contributor screening. Checking them alongside the checkout produced 16 R1 keyword-mismatch findings. All 13 affected type names, including `TESForm`, already have conflicting `class` and `struct` spellings in the existing reconstruction. The generated files introduce zero new conflicting names. The emitted template arguments retain their RTTI spellings. Resolving the shared declaration conflicts remains work for reconstruction integration.

The next opportunity is the ordinary teardown group. Distinguishing folded symbols or finding an independent owner for each address would make its 6,136 candidate bytes actionable.
