## Question and method

The Mudcrab lead needs the live value of `k` (haze trace #1077 and the NEEDS 19 spot-check found two run-time stores to the global), the target and state of the composite pass, and whether `k` reaches grass twice. Method: the author re-read all references to the global `0x20d694c`; decoded the two store sites and the console command record; traced the order of calls in `Main::Render`, `Main::Draw` and `0x1539f10`; decoded the composite function's target, texture, and state writes; traced the pass that fills the scene copy; traced the depth source to the creation of depth target 7; decoded the image-space shader base class virtual functions that run for the draw; re-read records 49, 51 and 53 for their texture use; mapped the grass technique ids to the first-stage draw windows; re-read the grass pixel record tails and the grass fog vector writers; and evaluated the net factor in single precision for invented values.

## Observations

### G01. Every writer and reader of `k`, and what the two run-time stores compute

**Verified.** A scan of the whole saved listing for every operand that resolves to `0x20d694c` finds 22 references: three stores (`0x37ac8f`, `0x116acfb`, `0x116afb6`) and 19 reads (18 by the readers listed below, and the load of the old value at `0x116aceb`). No `lea` of the address exists. The address is the field `invFrameBufferRange` of the PDB type `BSShaderManager::State` (`CRASHLOGGER_PDB`): the field offset in that struct is `0x9c`, and `0x20d694c − 0x9c = 0x20d68b0`, which is the base the code reads as an array of four scene node pointers (first field of that struct). That base match is **inferred**. A scan of the 241 references to `0x20d68b0` (11 take its address, 230 read or compare the first field directly) found no access at offset `0x9c` through a base register, and found no whole-struct copy. The only function that receives the base address as an argument is the destructor-like routine at `0x14eb570`, which releases texture pointers and does not touch `0x9c`.

**Verified.** Store (a), `0x37ac8f`: in the handler `0x37ac30`. The handler calls the argument parser `0x344ca0`. If it returns false the handler returns. If it returns true, the handler stores `1.0f / x` with `x` = the parsed float (the local is zero-initialised before the parse). The constant 1.0 is the float at `0x1b5be28`. The only reference to the handler address is the pointer in the command record at `0x2092770` (pointer at `0x20927a0`). The record has: name `SetFramebufferRange`, short name `sfbr`, opcode `0x214`, help text "Set frambuffer range", one parameter. The parameter record at `0x2096970` has type 2 (float) and the optional flag 0 (required). No code calls the handler directly. So the writer runs only when the console command runs. It applies no clamp or test of `x`: for `x = 0` the divide gives infinity, for `x < 0` a negative `k`, and `x = 2` gives `k = 0.5` (IEEE arithmetic; the runtime result was not run).

**Verified.** Store (b), `0x116acfb`: in `0x116ac80` (PDB `Renderer::MenuManagerDrawInterfaceStartHook`). If the byte at `[[0x219e5c0]+0x1c0]` is zero the function skips all of this. If it is non-zero, the function loads the current `k` into a register (`0x116aceb`), stores the **constant 1.0** from `0x1b5be28` (`0x116acfb`), draws the interface (it walks the array at `[object+0x110]`, count at `+0x120`, and calls a virtual slot of each entry), and stores the saved value back at `0x116afb6`. This site does not divide. The identity of the object at `[0x219e5c0]`, and of the byte at `+0x1c0`, was not resolved.

**Verified.** The 18 readers, by function: fog writer `0x154c010` (`0x154c07b`), composite function `0x1541f40` (`0x1543019`, uploads `k` to `cb2[1].w` and `cb2[2].w`), grass setup `0x1522520` (`0x152262a`) and its helper `0x15233c0` (`0x1523407`), the composite-like builder `0x1541230` (`0x154146c`), sky function `0x15525b0` (`0x1552964`, `0x1552990`), water `BSWaterShader::SetupTechnique` `0x154d330` (`0x154d5e1`) and `0x154d700` (`0x154dc46`, divides by `k`), effect shader `0x1556840` (`0x1556927`), `0x1558fd0` (`0x15591cc`, `0x15592e4`), `0x1579b10` (`0x1579eaa`, `0x157a38a`), bright-pass setup `0x15836d0` (`0x1583cbd`, `0x1583d05`, `0x1583d7d`) and `0x5282a0` (`0x528597`). All read the one global. The readers were located, and only the composite (G03–G06) and grass (G07–G08) uses were re-decoded here.

**Confidence: high** for the store list and both formulas. A write watch on `0x20d694c` for one frame would settle indirect writers (a plugin or injected code).

### G02. The live value in an ordinary exterior frame, and the timing of the interface store

**Verified.** The image value is `0x3f555555` (0.8333333134651184), which equals `1.0f / 1.2f` (the float division gives the same bit pattern) and `B / 1.2` with `B = 1.0`. No INI key, game setting, weather value or image-space value feeds the global. The earlier finding (#1061 G06) and the grass leftovers finding already reported the three stores. This finding adds that (b) is a constant, not a reciprocal.

**Verified.** Order inside one `Main::Render` pass (`0x6565b0`). The world render wrapper `0x656d10` (it calls `Main::Draw` `0x656e60`, which calls `0x1539f10` at `0x6576be`) is called at `0x656834` and at `0x656a78`. Control from `0x656a78` goes to `0x65689f` (jump at `0x656aaf`). Control from `0x656834` continues through the test at `0x656886` to `0x65689f` (both outcomes of that test reach `0x65689f`). From `0x65689f` the flow reaches the interface wrapper call at `0x656921`. So in one pass both world render call sites come before the call that sets 1.0, and the old value is restored when the wrapper returns, before anything else in `Main::Render` runs. A third call of `0x656d10` is at `0x656cc8` in the separate function `0x656c50` and was not traced. The wrapper has a second caller, `0x6e4dc0` in `0x6e4c20`, which is called from `0x60f27e` in a function the PDB calls `UISaveLoadManager::ProcessEvent`. Its purpose and whether a world render can run inside it were not traced.

**Inferred.** For the world colour pass of an ordinary frame the composite upload reads `k = 0.8333333` and the grass setup reads the same value. No store changes the global between the first stage draws and the composite upload within the pass (`0x1539f10` has no store to it, and none of the functions it calls was found to write it, per the reference scan).

**Verified (formula).** `k` for ordinary frames = `1.0f / FramebufferRange` with `FramebufferRange = 1.2f` (image) unless `sfbr x` was run (`k = 1.0f / x`). Default value `0.8333333`, `1/k = 1.2000000477` (single precision), `k² = 0.6944444`.

**Unverified.** Whether the world render runs while the interface wrapper is active in any path (a virtual call in its array could in principle reach it; none was seen). What the byte at `+0x1c0` means. Whether `sfbr` is typed in a given session.

**Confidence: high** for the value and formula. **Medium** for "constant 0.8333333 for the whole world pass", which rests on the call order and the reference scan.

### G03. The composite call: output target, `t0` source and the pass that fills it

**Verified.** The composite call is at `0x153a1ca` inside `0x1539f10`: `edx = 0x71`, `r8d = 1`, `rcx` = `[manager + 0x1c8]` (the SAO effect set that holds the three composite effects; manager global `0x33d40a0`). The first call at `0x153a102` passes 1 and 1 (SAO generation only, #1077 G04). In the composite branch (`0x1542986`) the function first calls the render-target setter `0x10155b0` with `(slot 0, target r8d, mode 3)` at `0x15429af`. That setter stores the target index in the render-target slot array at `0x20cfc18 + 4×slot`. Other callers show the argument order (slot, target): in `Main::Draw` slot 1 gets target 7 (`kMOTION_VECTOR`) and slot 2 gets target 4 or 5 (`kNORMAL_TAAMASK_SSRMASK`, `_SWAP`) before `0x1539f10`. So the **output** of the composite is target **1** (`kMAIN`). The first-stage target is also target 1: `Main::Draw` binds slot 0 to target 1 at `0x657573–0x65757e` before the call to `0x1539f10`.

**Verified. Correction to #1077 G08 (see C1).** The value `0x71` selects the shader resource that the function stores at `0x20cfd40` (code `0x15429b4–0x15429e3`). That address is the first entry of the pixel shader resource array, not a render target slot (G04 shows the consumer).

**Verified.** The render target table (base `0x3331f40`, stride `0x30`) has the shader resource pointer at `+0xa70` and the render target view at `+0xa68` of each entry. The index `0x71` = 113 = the PDB enumerator `kSNOW_SWAP` (the enumerator list ends with `kSSR` 109, `kSSR_RAW` 110, `kSSR_BLURRED0` 111, `kSNOW_SPECALPHA` 112, `kSNOW_SWAP` 113). The description for entry 113 is built at `0x153ba2c–0x153ba5e` and created at `0x153ba9f`: width and height are the output size globals `0x33363c4` and `0x33363c8` (the same size as target 1), format `0x1a` (DXGI 26, `R11G11B10_FLOAT`) fixed, and one extra flag word `0x100` that other full-size colour targets lack. The meaning of that flag word is **unverified** (a UAV flag would fit the compute copy below, **inferred**). Target 1 itself takes the format `0x1a`, or `0x0a` (`R16G16B16A16_FLOAT`) when `bUse64bitsHDRRenderTarget` is set (#1059 G02). So with that setting the copy target and the main target differ in format.

**Verified.** Between the SAO generation call and the composite call, `0x1539f10` (`0x153a110–0x153a19b`) fills target 113 from target 1:
- If byte `0x20d6ce8` (image value 1) is set and the byte at `+8` of the object at `[manager + 0x1e8]` is set, it calls `0x1544ab0(effect, 1, 0x71)`. That function binds target 0x71 as output slot 0 and binds target 1 and two global textures as inputs, and draws the effect. By the PDB layout of `ImageSpaceManager` (size `0x220`, offsets counted from the end of the struct, **inferred**) `+0x1e8` is `BSImagespaceShaderISSnowSSS`.
- Otherwise it sets up and dispatches the compute shader at `[manager + 0x198]` (`0x1540ef0` with source index 1 and destination 0x71, `0x1540f70`, then `0x1540db0`, which calls the compute dispatch with `ceil(w/8)`, `ceil(h/8)` groups). By the same layout `+0x198` is `BSImagespaceShaderISCopySubRegionCS`. The rectangle has origin (0, 0) and its size comes from the globals `0x333561c` and `0x3335620` (their relation to the output size globals `0x33363c4`/`0x33363c8` was not checked). The two indices (1 and 0x71) are stored in the compute call object at `+0x30` and `+0x34`, and the call object's mode 2 binds one as input and one as output.
Then `SetRenderTarget(slot 0, none)` runs and the byte `0x14343639c` is set to 1. So `t0` of the composite holds a copy of the first-stage scene colour. With the snow effect active it holds that effect's output instead (its arithmetic was not decoded).

**Inferred.** The composite therefore reads one copy (`kSNOW_SWAP`) and writes the original (`kMAIN`) as a full-screen replace. The name `kSNOW_SWAP` is the PDB's label, and its role here (scene colour copy) is read from the code.

**Confidence: high** for the output target, the `0x71` role, the format and the two fill paths. **Medium** for the manager member identities (layout counting). **Unverified:** which fill path is active in a retail exterior frame (`0x20d6ce8` image value 1, but the effect's `+8` byte was not traced), and the snow effect's arithmetic.

### G04. Texture bindings, and the depth source

**Verified.** In the composite branch the function writes seven shader resource pointers to `0x20cfd40 + 8×slot` and sets bit `slot` in the dirty mask at `0x20cfc04` for each change (`0x15429b4–0x1542b0c`):

| Slot | Source | Role |
|---|---|---|
| `t0` | target 113 (`kSNOW_SWAP`) resource at `+0xa70` | scene colour copy (G03) |
| `t1` | target `0x2e + byte[0x143436398]` (46 or 47, `kSAO`, `kSAO_DOWNSCALED`; selector byte not traced) | AO factor `A` |
| `t2` | depth target `[0x14333637c]`, resource at `+0x20a0` of a `0x98`-byte entry | depth (below) |
| `t3` | target from `0x153c900` (4 or 5, `kNORMAL_TAAMASK_SSRMASK` or `_SWAP`) | mask tested by the SSR branch (#1077 G05) |
| `t4` | global pointer at `0x3333eb0` | snow term texture |
| `t5` | global pointer at `0x3332d10` | texture used only by the sparkle branch |
| `t6` | target 109 (`kSSR`) or 110 (`kSSR_RAW`) by byte `0x3436378` | SSR colour and alpha |

**Verified.** The consumer is the resource flush in `0x1010de0` (`0x10113c4–0x1011405`). For each set bit of `0x20cfc04` it calls the device context virtual at offset `+0x40` with start slot = the bit, count 1 and a pointer into `0x20cfd40`. Offset `+0x40` is the eighth virtual of the D3D11 device context, `PSSetShaderResources`. The render target flush `0x100a050` calls offset `+0x108` (`OMSetRenderTargets`) with the slot array at `0x20cfc18`, and the state flush at its end calls `+0x118` (`OMSetBlendState`). So `0x20cfd40` is the pixel shader resource array.

**Verified.** The depth index `[0x14333637c]` is set to 7 at `0x1539f65` at the start of `0x1539f10` (the interface wrapper sets it to the main depth index, which `GetDepthStencilTarget_MAIN` returns as 0, at `0x116ad20`). The depth entry 7 is created at `0x153c13e–0x153c15f` with the full output size and the flag word `0x100`. `RenderDepth` (`0x1538fa0`) is called from `Main::Draw` at `0x657213`, before `0x1539f10` (`0x6576be`). It binds main depth target 0 with all colour targets unbound, draws the depth prepass with the accumulator at `[0x3436228]`, and ends with a `CopyResource` call (device context virtual `+0x178`, `0x1539df`) whose destination is the texture of depth entry 7 (`0x3334380`) and whose source is entry 0 (`0x3333f58`). Between that copy and the world render `Main::Draw` runs other calls (`RenderShadowmasks` `0x1539a70`, a stub `0x153a630`, the camera and writer set `0x14101c660`, and `PrepareMainDepthPrepass` `0x1537f60`, which rebinds depth target 0 and clears it when byte `0x20d72e8` is set). None of them was found to write depth entry 7. The only other direct reference to the entry 7 texture pointer is a second `CopyResource` (main depth to entry 7) at `0x151f2c2` inside the first stage `0x151ef40`. It runs only if bit 7 of the stage's flag word is set and the second stage's default list holds passes in `[0x5c000071, 0x5c006071]`. `0x1539f10` passes the flag word `(argument << 4) | 0x41` (`0x153a021`), which is `0x41` or `0x51`, so bit 7 is clear and that second copy is skipped in this frame.

**Verified.** So `t2` is the shader resource view of a **copy of the main depth buffer taken after the depth prepass and before the first colour stage**. It is **raw hardware depth**, not a linearised value. The composite record linearises it (record 53: `d' = 1.01×d − 0.01`, `ndc = 2d' − 1`, `z = 2NF/((N+F) − ndc×(F−N))`, as in #1077 G05). The pixel read is the first channel of the resource. **Unverified:** which geometry the prepass accumulator draws. Pixels where no prepass draw wrote depth keep the cleared value and fail the `d < 0.999999` test, so they skip fog and the `k` scale (#1077 G05). Which classes (terrain, terrain LOD, object LOD, near objects, grass) are in the prepass was not traced. The prepass accumulator is the object at `0x3436228`. `RenderDepth` draws it through `RenderCameraView` with flag word `0x21` (`0x153911b`). The `Main` constructor sets its mode field (`+0x150`) to 12 (`0x140651901`). The mode table at `0x1433d4b20` is zero in the file and is filled at run time (`0x14eab1e–0x14ead24`). Entry 12 is `BSShaderAccumulator::FinishAccumulatingSharedModes` (`0x1415206a0`, `CRASHLOGGER_PDB(59818@2026.10.24)`). With flag bit 8 clear, that handler draws the id windows `[0x2b, 0x4000002b]` and `[0x5c000030, 0x5c00005c]`. The second window contains the grass ids `0x5c000030..0x5c00005c` (G07). Ids 3 to `0x14` fall in neither window. The windows alone therefore neither include nor exclude grass. Whether the grass shader property builds passes for this accumulator was not traced. **Unverified.** The prepass also uses a depth shift convention that was not compared with the `1.01`/`−0.01` remap.

**Confidence: high** for the bindings, the PS resource flush and the depth copy. **Unverified:** prepass membership and the shift convention.

### G05. State of the composite draw: blend, depth, write mask

**Verified.** The composite function sets no blend group, no alpha-to-coverage and no depth state of its own. It zeroes sampler state words (`0x20cfcbc`…`0x20cfd14`, the pairs seen in #1077 G08, which are sampler slot caches) and then runs the effect.

**Verified.** The draw goes through `BSImagespaceShader::Render` (`0x1565090`, pass id `0x5c006076`) and `BSBatchRenderer::SetupAndDrawPass` (`0x1560340`). That function calls the shader's virtual at offset `+0x10` with the pass id. For the three composite classes (same vtable slots) the virtual at `+0x10` is `0x1564960`. It sets the colour write mask mode (`0x20cfcb0`) to the value in `0x20d910c`, clears the alpha test byte (`0x20cfcb4`) and sets the depth mode (`0x20cfc88`) to 0. The restore virtual at `+0x18` is `0x1564a00` (mask mode 1, depth mode 3). The slots `+0x50` and `+0x58` of these classes are empty stubs. With the mask mode and depth mode tables from the sky finding (mask 1 = RGB, mask 2 = RGBA; depth 0 = test off, no write) the composite draws with no depth test and no depth write. `0x20d910c` has the image value 2 (RGBA). It is written only in short windows by other code (`0x1406569cf` sets 1 around a different effect call; `0x14152ebf1`, `0x1415306be` and others were not placed). It is not written between the SAO generation call and the composite call in `0x1539f10`.

**Unverified (value at the draw).** The blend group cache `0x20cfca8` at the composite draw. No function in the effect path writes it (the composite function, the image-space setup and restore slots `0x1564960` and `0x1564a00`, the snow pass `0x1544ab0` and the compute copy `0x1540db0`). The first stage `0x151ef40` sets blend group 0 at `0x151f25f` (the register holds zero, set at `0x151f0e4`; the store runs when the cached value is not zero), with colour write mask mode 1 at `0x151f278`, after the decal passes. No later writer of the group was found between that store and the composite draw. So group 0 ("off", one and zero in the sky finding's table) is the best supported value. This is **inferred, medium**: not every path from `0x151f25f` to the composite draw was traced, and a capture would settle it. The flush uses it with `0x20cfcac`, the mask mode and `0x20d01d0` to pick a blend state object (`0x100a36c–0x100a3ba`). The sky shader restores group 0 after each draw (`0x1552190`, sky finding G10); the other shaders' restore paths were not read. The virtual slots `+0x10` (`0x1564960`) and `+0x18` (`0x1564a00`) are the generic image-space implementations (the address occurs in about 118 vtables). The vtables of the three composite classes were not checked one by one. The shader output is the full scene result with `k` already applied, which fits a replace write (group 0, one and zero). This fit is **inferred**, not read.

**Confidence: high** for the depth and mask state and the absence of blend writes in the effect path. **Medium** (inferred) for blend group 0 at the draw; the value at the draw is unverified. A device capture of the blend state at that draw would settle it.

### G06. The three composite records and their binding set

**Verified** (re-read in the saved decodes). Records 49 (`ISSAOCompositeSAO`), 51 (`ISSAOCompositeFog`) and 53 (`ISSAOCompositeSAOFog`) all use `cb2` with 11 elements and `cb12` with 45. Records 49 and 53 declare `t0`…`t6` and `s0`…`s6`. Record 51 declares `t0` and `t2`…`t6` (six resources, six samplers) and has no `t1`. Record 53 samples `t0`, `t1` and `t2` unconditionally, and `t3`, `t4`, `t5` and `t6` conditionally. Record 49 samples `t0`, `t1`, `t3`, `t4` and `t6` as record 53 does. It samples `t2` and `t5` only inside the sparkle branch (for the world position), and it applies no fog term and no `k`. Record 51 samples `t0`, `t2`, `t3`, `t4`, `t5` and `t6`. The composite function binds all seven slots before it picks the effect (G04, and #1077 G04 for the pick). A record that does not declare a slot still has it bound. The arithmetic of record 53 re-read here agrees with #1077 G05, including `d < 0.999999` on the raw depth channel, `k × cb2[1].w` after the fog blend, and `rgb = A × C` (no `k`) for the other pixels. The generic effect used when both settings are 0 (#1077 G04, index `0x22`) was not decoded.

**Confidence: high.**

### G07. Grass draw order against the composite

**Verified.** The grass technique selector `0x1522520` (and the twin lookup in `0x15233c0`) maps pass ids to techniques. Pass ids `3` to `0x14` use a jump table, id `0x5c000030` selects technique 1, and ids `0x5c000031` to `0x5c00005c` use a byte table (`0x15227dc`) and a second jump table (`0x15227c0`). All other ids default to technique 0. So the grass shader's pass ids lie in `[3, 0x14]` and `[0x5c000030, 0x5c00005c]`.

**Verified.** The first stage `0x151ef40` draws the default list over the id windows `[1, 0x5c00002f]` and `[0x5c000030, 0x5c00005c]` (taken from #1061 G03 and the sky draft G11, which list the same windows; the windows were not re-read here). Both grass windows are inside them. The second stage `0x151f540` draws the default list over `[0x5c000071, 0x5c006071]` and the sorted groups. No grass id lies in that default window. The composite call `0x153a1ca` comes after the first stage (`0x153a02f`) and before the second stage (`0x153a1ef`) (#1077 G04).

**Inferred.** A grass pass goes to the default list: the generic `BSShader::MakeRenderPass` (`0x1555820`) stores category 0 at pass `+0x1c`, and category 0 takes the default list (#1061 G03). Whether the grass shader's own pass builder changes the category was not read. If a grass pass went to a stage 2 group list instead, the order would change.

**Result:** the grass colour draws are in the first stage, before the composite, by id windows (verified) and category (inferred). **Confidence: medium.** The grass pass builder and the group registration of grass passes would settle it, or a draw capture. Separately, whether grass is in the depth prepass is open (G04).

### G08. The grass pixel tail and the source of `cb2[16].w`

**Verified** (re-read in the saved decodes). The 18 pixel records of group 2 split into two kinds. Records 7, 8, 16 and 17 output a depth-like value (`o0.w` from a test, `o0.xyz = v4.x / v4.y`, with `discard`), they do not read `cb2[16]` and are not colour passes. The other 14 records (0–6 and 9–15) end with `o0.rgb = (lit grass colour) × cb2[16].w` and `o0.a = 1.0`, then write a motion vector in `o1` and a normal pack in `o2`. They contain no fog term. The tail multiply is the last operation on the colour.

**Verified.** `cb2[16]` takes its value from the global vector at `0x33d4d50`. The grass setup writes that vector once per technique setup, in two places: `0x1522520` (stores at `0x1522611` and `0x152264e`) and `0x15233c0` (stores at `0x15233eb` and `0x152342b`). With a scene fog property (GUESS label, see the getter note below) present: if both distance floats (property `+0x50`, `+0x54`) are zero it stores the constant `(0, 0, 0, 1)` from `0x17eab80`, so `cb2[16].w = 1.0`. Otherwise it stores `(near fog RGB, k)` with `k` read from `0x20d694c` at that moment, so `cb2[16].w = k`. With a null property it leaves the vector as it was (image value all zeros; the exterior startup installs a property, per the grass leftovers finding). The property getter is `0x14ec040`. The PDB names that function `BSShaderManager::GetPortalGraph` (`CRASHLOGGER_PDB(59818@2026.10.24)`). It returns the pointer at `+0x220` of the node selected by the index in a four-entry array at `0x20d68b0`. Its role as a scene fog property getter is GUESS, from how its result is used (colour at `+0x38..+0x40`, distances at `+0x50` and `+0x54`). The copy of the vector into `cb2[16]` is from the grass leftovers finding and was not re-read here.

**So** the grass PS scale `k_g` is `k` when the scene fog property has a nonzero fog distance, and 1.0 when both are zero. `k_g` and the composite `k` come from the same global in the same frame (G01, G02).

**Confidence: high** for the PS tail and the vector writes. **Medium** for the cb2 binding (taken from an earlier finding).

### G09. Net factor on a grass pixel

**Derived (inferred) from G03–G08.** Take a grass pixel drawn in the first stage with the colour `k_g × G` (opaque write, alpha 1; the blend state is unverified, G05) and the depth-copy value `d` under it. After the composite with the default record 53 and no snow or SSR term:

- if `d < 0.999999`: `final = saturate( k × ( (1−Fc) × A × k_g × G + Fc × Cfc ) )`, per channel. `Fc` and `Cfc` come from the depth `d` (not from the grass depth), `A` from the AO texture.
- if `d ≥ 0.999999`: `final = saturate( A × k_g × G )`.

With `k_g = k` (a scene fog property with a nonzero distance): the colour term has `k²` and the fog term has `k¹`. At `Fc = 0` the net factor on `G` is `k^n` with **`n = 2`**, which is `0.6944444` at the image value. With `k_g = 1` (both fog distances zero) `n = 1` for the colour term. For a Lighting pixel at (S,T) = (1,0) the same formula holds with `L` in place of `k_g × G` and no `k` in the PS (`out = L` while `k×M ≤ B`, #1061 G05), so its colour term has `n = 1`. So, under these readings, an opaque grass pixel gets one more factor `k` than an opaque Lighting pixel at `Fc = 0`.

Example in single precision (invented values: `G = L = 0.4`, `Cfc = 0.6`, default `k`, `d < 0.999999`):

| `A` | `Fc` | grass final | Lighting final | grass PS output alone (no composite) |
|---|---|---|---|---|
| 1.0 | 0 | 0.27778 | 0.33333 | 0.33333 |
| 1.0 | 0.5 | 0.38889 | 0.41667 | 0.33333 |
| 1.0 | 1.0 | 0.50000 | 0.50000 | 0.33333 |
| 0.8 | 0 | 0.22222 | 0.26667 | 0.33333 |

**What supports it.** The PS multiply (G08, verified), the stage order (G07, verified by ids, inferred by category), the composite arithmetic and `t0` (G03, G06, verified), and the same global for both factors (G01, G02, verified). **What is unverified:** (a) the prepass membership, so the value of `d` under a grass pixel (grass over terrain is most likely under a terrain depth in the copy, but this was not traced; if `d ≥ 0.999999` the grass pixel gets `n = 1`); (b) the blend state of the grass draws and the composite; (c) the snow, SSR and sparkle terms; (d) the runtime value of `k_g` (the fog distances of the active weather). **No visual claim** is made (whether the extra factor is visible, or a design choice).

**Confidence: medium.** A capture of `t0`, `t2` and the grass output at one pixel, or the prepass accumulator's membership, would settle it.

### C1. Correction to earlier finding: #1077 G08 (render target slot 0)

**Scope: #1077 G08, the second "Observed. Meaning unverified." paragraph only.** The published text says the composite function "uses [the `0x71` argument] as an index into the render target table at `0x3331f40` (stride `0x30`, pointer at `+0xa70`) and stores the pointer into render target slot 0 of the renderer state (`0x15429b4–0x15429d9`, store at `0x20cfd40`). The identity of table entry `0x71` is unresolved here."

**Correction. Verified, high.** The store at `0x20cfd40` goes to the pixel shader resource array, not to a render target slot. The dirty-bit flush at `0x1010de0` passes `0x20cfd40 + 8×slot` to the device context virtual at `+0x40` (`PSSetShaderResources`), and the render target slots are the index array at `0x20cfc18` (consumed at `0x100a050` through `OMSetRenderTargets`). The pointer at `+0xa70` of table entry `0x71` is the shader resource view for texture slot `t0`. The output target is set separately, to target 1 (`kMAIN`), with the setter call at `0x15429af` (G03). Table entry `0x71` is the PDB enumerator `kSNOW_SWAP` (113).

**This PR amends that paragraph** (see "Amendments in this PR"). **Not an error:** the "Observed. Meaning unverified." label and the statement that the identity of entry `0x71` was unresolved were honest. The same G08 paragraph's other statements are not contradicted. The Answer table and all arithmetic claims of #1077 are unaffected. The related open items of #1077 G05 (`t2` binding), G07 (grass order) and G08 (blend) are answered or narrowed in G04, G07 and G05 above.

**Scope: the sky finding (`findings/sky-sun-ambient-day-retail-facts.md`, merged as #1080), G09 only (the vertex stage paragraph).** The G13 table row "sky `k`" says only "initial file value; run-time global, see G09" and needs no change. ## Interpretation and alternatives

- The composite is a scene-copy-to-main full-screen replace with fog and `k`. The `0x71` role as `t0` source resolves the main open item of #1077 G08. The depth source resolves its G05 inference ("raw hardware depth") with one refinement: it is a post-prepass copy.
- The grass result depends on one open question that is cheap to settle with a capture and costly to settle statically: which geometry enters the depth prepass. If grass or the terrain beneath it is outside the prepass, the grass pixel has `d = 1.0` in the copy, takes the `A × C` branch, and gets no fog and no second `k`. This would also apply to any other class that is outside the prepass, including the classes #1077 treats as fogged. #1077 did not claim prepass membership, and this finding did not trace it.
- `k_g` is 1 when both scene fog distances are zero. Whether any weather or the exterior startup property gives two zero distances while grass draws is unverified (grass leftovers G17).
- `bSAOEnable`/`bSAOApplyFog` choose the record (#1077 G04). With `bSAOApplyFog = 0` and `bSAOEnable = 1` (record 49), the composite applies no fog term and no `k`. The net factor on grass is `k_g` (`n = 1` when `k_g = k`) and Lighting pixels have `n = 0`. With record 51 (no AO term, `A = 1`) the net factor on grass is `k × k_g`. With both settings 0, the generic effect `0x22` runs and was not decoded.
- The snow path (`0x20d6ce8`) changes `t0`'s source. Its pass was not decoded.

## Negative results and limitations

- No capture, no live constant read and no visual comparison. All claims are static.
- Not traced: the blend group cache value at the composite draw (group 0 is inferred, medium), whether the grass shader property builds passes for the prepass accumulator, the vtables of the three composite classes for slots `+0x10` and `+0x18`, the prepass geometry set and its depth shift, the grass pass builder category, the grass `cb2[16]` copy, the object `[0x219e5c0]` and its byte `+0x1c0`, the purpose of the second wrapper caller (`0x6e4dc0` via the save/load handler) and the third world-render call (`0x656cc8`), the effect `+8` enable byte and the snow effect arithmetic (so the content of `t0` when the snow effect runs), selector bytes `0x3436398` and `0x3436378`, flag word `0x100` of the target descriptions.
- Not excluded by the scan: a write to `0x20d694c` through a pointer built at run time (for example by injected code). No such pointer arithmetic was found in the 241 base references and the 22 direct references.
- The manager member names (`ISCopySubRegionCS`, `ISSnowSSS`) come from counting the PDB struct layout from the end (`0x1e8`, `0x198`, `0x1c8`, `0x1c0` all fit). The layout was not matched to constructor code.

- `llvm-objdump` was used for the single functions. The saved full listing was used only for reference scans.
